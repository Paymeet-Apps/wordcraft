# Arabic Interface (RTL) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** WordCraft's interface can be shown in Arabic: every string translated, Arabic letters joined and ordered correctly, and the whole chrome mirrored (ribbon, menus, panes, dialogs, status bar), selectable in File › Options › Interface language or picked automatically from an `ar-*` system locale.

**Architecture:** Three layers, each usable on its own. (1) A `bidi` module turns a logical string into the order egui must draw it in, and `i18n` uses it for every catalog string and `fmt` result when the interface language is right-to-left. (2) An `rtl` module gives direction-aware replacements for the LTR-only egui idioms the UI uses (`ui.horizontal`, `Layout::right_to_left`, `Align2::LEFT_*`, `egui::Grid` rows, painter x-coordinates), and each UI surface switches to them. (3) An `ar.tsv` catalog plus an Arabic UI font. The direction comes from one flag, `LangInfo::rtl`, so Hebrew (PR #20) later needs only a catalog and `rtl: true`.

**Tech Stack:** Rust, egui/eframe 0.36 (epaint 0.36.2 shapes with harfrust 0.12, but has **no bidi**), `unicode-bidi` 0.3 (already a workspace dependency), `egui_kittest` for UI tests, craft-fonts for the Arabic face.

**Spec:** No separate spec. Requirements come from `docs/localization-parity.md` (Arabic row: "shaping, joining, lam-alef, bidi ✅ (#207); no kashida; **no mirrored UI**"; Shared work: "Mirrored (right-to-left) interface for Arabic and Hebrew, 15–25 h") and `CLAUDE.md`. Translation conventions: `crates/ui-egui/src/i18n/mod.rs` header and the `fr.tsv` header.

## Global Constraints

- Never crash: no `unwrap`/`expect`/`panic!`/indexing on input-derived data outside tests; bidi code takes catalog and user strings, so it treats them as hostile (slice only at char boundaries, `get()`, no recursion).
- Clean room: translate from the English meaning. Ribbon tab, group and command names may use the names Arabic Word users know (feature names). No other Microsoft wording, and nothing copied from Word's `ar.lproj`.
- Assets: the Arabic font goes to `storytold/craft-fonts` with its row in that repo's attribution file, **never** into this repo. Candidate: Noto Sans Arabic UI (SIL OFL 1.1), Regular/Medium/SemiBold to match Inter's three families. Pushing to craft-fonts is the owner's call (see Task 4).
- Command ids, document text, saved files, the control channel, CLI and MCP never see translated or reordered text (`i18n/mod.rs:3-5`).
- The document canvas is **not** mirrored (Word doesn't mirror pages for an Arabic interface). RTL paragraphs keep working as they do today (#207, #692).
- Digits in the interface stay Western (0–9). Arabic-Indic digits in documents remain `view.numeral` (#501).
- Count labels use count-neutral wording (`الكلمات: {words}`), because Arabic has six plural forms and the catalog has no plural support.
- `cargo xtask ci` green before every commit (fmt, clippy -D warnings, tests, assets, layers, wasm). Commit messages: `L10N-AR.<task>: <summary>`.
- No new crate dependencies. `rtl`/`bidi` live in `crates/ui-egui` (L6). If the fonts crate needs bidi it already has `unicode-bidi`.

## Non-goals (tracked as follow-ups, not built here)

- Arabic proofing (spelling, grammar). `editing_lang` stays `None` for `ar`.
- Editing Arabic inside egui `TextEdit` fields (Find box, command search, font name box): egui's caret and selection logic is logical-order and LTR. Arabic typed there will draw correctly once Task 2 is in, but caret placement and selection inside an Arabic run will be off. File as a follow-up issue in Task 16.
- Scroll bars of egui `ScrollArea`s on the left. egui 0.36 always draws them on the right. Only the document's own vertical scroll bar (`scroll.rs`) moves (Task 10).
- Kashida justification (layout-parity item).

## Review Focus

1. **Mixed-direction strings with filled placeholders:** an English file name in an Arabic message (`تم الحفظ: report.docx`), an Arabic file name in an Arabic message, and digits (`صفحة 3 من 9`) must read correctly right to left. Tests: Task 3 `fmt_isolates_inserted_values_in_rtl`.
2. **Switching language at runtime** (en → ar → en in one session): the next frame must be fully mirrored, then fully unmirrored, with no stale fonts, cached ribbon widths or keytip positions left over. Tests: Task 5 `switching_to_arabic_and_back_restores_fonts`, Task 8 `ribbon_mirrors_and_unmirrors_on_language_switch`.
3. **No Arabic font available** (built without craft-fonts, wasm, minimal Linux with no Noto Arabic): selecting Arabic must not crash or hang. Text may show boxes, a warning is logged once, and English keeps working. Test: Task 4 `arabic_interface_without_any_arabic_font_does_not_panic`.
4. **Keyboard direction in RTL:** in the ribbon, menus and keytips, Left/Right arrows move to the visually adjacent item (Left = next item in RTL). Test: Task 8 `arrow_keys_follow_the_visual_order_in_rtl`.
5. **Narrow windows:** the ribbon collapses groups from the visual end (the left side in RTL), and nothing overflows past the left edge at 800 pt wide. Test: Task 8 `narrow_arabic_ribbon_collapses_from_the_left`.

### Task 2: `bidi::visual`: logical text → draw order (Strategy A, confirmed by Task 1)

Task 1's findings (see the `//!` doc of `bidi.rs`): epaint shapes each run of Arabic-face glyphs right to left and joins it, but spaces, punctuation, digits, brackets and Latin come from Inter as **separate runs in logical position**, nothing is reordered, and brackets are **not** mirrored. So inside every right-to-left (odd-level) bidi run, `visual` must itself order those neutral characters around the Arabic segments and mirror the brackets.

**Files:**
- Modify: `crates/ui-egui/src/bidi.rs`

**Interfaces:**
- Produces:
  - `pub fn visual(s: &str, base_rtl: bool) -> std::borrow::Cow<'_, str>`: one line of text in the order egui must draw it. `Cow::Borrowed` when `s` has no strong RTL character and `base_rtl` is false, and also when it is a single RTL run under Strategy A. It never panics, and its output contains no bidi control characters.
  - `pub fn first_strong_is_rtl(s: &str) -> bool`: the direction of the first strong character (UAX #9 P2); false when there is none.
  - Placeholder rule: every `{name}` token (ASCII `[A-Za-z0-9_]+` between braces) is treated as an LTR isolate, so it comes out contiguous and unchanged. Implement this by wrapping each token in U+2066 LRI … U+2069 PDI before running `unicode_bidi::BidiInfo::new(text, Some(Level::rtl()))` (or `Level::ltr()`), then strip the controls from the output.
  - Multi-line input: split on `\n`, convert each line separately, rejoin with `\n`.
  - Inside each odd-level run: split it into segments. A segment is either a maximal sequence of strong right-to-left characters (bidi class `R` or `AL`) together with the `NSM` marks, ZWJ (U+200D) and ZWNJ (U+200C) inside or right after them, or one single other character. Reverse the order of the segments, keep each strong-RTL segment's characters in logical order (epaint shapes it), and replace each mirrored bracket with its pair: `(`↔`)`, `[`↔`]`, `{`↔`}`, `<`↔`>`, `«`↔`»`, `‹`↔`›`. Even-level runs are emitted unchanged.
